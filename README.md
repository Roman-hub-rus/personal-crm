# Личная CRM

Приложение для своих контактов: кто это, откуда знакомы, как связаться, о чём договорились.
Подробнее — `specs/01-продуктовая-идея.md`.

## Что нужно на компьютере

- Node.js 24 (LTS) и pnpm
- Docker Desktop — в нём работает база данных PostgreSQL

## Настройки подключения

Пароль и адрес базы лежат в файле `.env` в корне проекта. В git он не попадает.

Если `.env` нет (например, проект скачан заново):

1. Скопируйте `.env.example` в `.env`.
2. Заполните значения: имя пользователя, пароль, имя базы, порт (обычно `5432`).
3. Соберите из них строку `DATABASE_URL` по образцу из `.env.example`.
4. Заполните настройки входа (откуда берётся каждое значение — в `.env.example`):
   - `BETTER_AUTH_SECRET` — ключ, которым подписывается вход. Получить: `openssl rand -base64 32`, результат вписать после `=`;
   - `BETTER_AUTH_URL` — адрес приложения: `http://localhost:3000`;
   - `SMTP_URL` — куда слать письма со ссылкой для входа: `smtp://127.0.0.1:1025` (это Mailpit, см. ниже);
   - `MAIL_FROM` — адрес отправителя, локально подойдёт любой, например `noreply@localhost`;
   - `OWNER_EMAIL` — ваша почта: вам достанутся контакты, которые были до появления входа, и тестовые контакты.

## База данных

Все команды — в терминале, в папке проекта.

Запустить базу:

```sh
docker compose up -d
```

Проверить, что база работает (в колонке STATUS должно быть `healthy`):

```sh
docker compose ps
```

Остановить базу (данные сохранятся):

```sh
docker compose stop
```

База запускается сама вместе с Docker Desktop, пока её не остановили вручную.

Данные хранятся в Docker-томе `personal-crm_db-data` и переживают перезапуск компьютера и контейнера.
Команда `docker compose down -v` **удаляет все данные базы** — не запускайте её, если данные нужны.

## Почта для входа: Mailpit

Вход в приложение — по ссылке из письма. Чтобы на компьютере не слать настоящие письма, вместе с базой запускается Mailpit — почтовая заглушка. Все письма приложения оседают в нём и **никуда не уходят**.

Mailpit стартует той же командой `docker compose up -d`. Письма видны на странице http://127.0.0.1:8025 — открывайте её в браузере, когда приложение «отправило» ссылку для входа. Проверить, что Mailpit работает: `curl -s http://127.0.0.1:8025/api/v1/info` отвечает.

## Первый запуск

Все команды — в терминале, в папке проекта, по порядку:

```sh
pnpm install        # поставить библиотеки
docker compose up -d # запустить базу
pnpm db:migrate     # создать таблицы в базе (нужна строка OWNER_EMAIL в .env, см. ниже)
pnpm db:seed        # (по желанию) добавить 1000 тестовых контактов
pnpm dev            # запустить приложение
```

Затем откройте в браузере http://localhost:3000.

`pnpm db:migrate` берёт вашу почту из строки `OWNER_EMAIL` в `.env`. Если в базе уже есть контакты (они появились, когда входа ещё не было), миграция отдаёт их пользователю с этой почтой: войдёте под ней — увидите их все, ничего не потеряется. Если контакты в базе есть, а `OWNER_EMAIL` не задана, `pnpm db:migrate` остановится с ошибкой «OWNER_EMAIL is not set…» и ничего не изменит. Добавьте строку в `.env` и запустите команду ещё раз. В пустую базу миграция проходит и без почты.

`pnpm db:seed` добавляет тестовые контакты и группы пользователю с почтой из `OWNER_EMAIL`: если под этой почтой ещё никто не входил, пользователь создаётся. Войдёте под этой почтой — увидите тестовые данные, а любой другой пользователь увидит пустой список. Без строки `OWNER_EMAIL` команда остановится с понятной ошибкой.

`pnpm db:seed` добавляет контакты только в **пустую** базу. Если контакты уже есть, команда ничего не меняет.
Другое количество: `pnpm db:seed 200`.

Примерно у 3% тестовых контактов задано, как часто общаться. С частью из них давно не общались — они сразу видны на главной в блоке «Пора связаться».

В тестовых данных также есть шесть групп (Семья, Друзья, Знакомые, Коллеги, Теннис, Аналитики), и примерно половина контактов состоит в одной или нескольких из них.

## Обычный запуск

```sh
docker compose up -d   # база и Mailpit, если ещё не запущены
pnpm dev
```

Приложение открывается на http://localhost:3000. Открывайте именно этот адрес (он же `BETTER_AUTH_URL` в `.env`): `localhost` и `127.0.0.1` для браузера разные адреса, и вход, сделанный на одном, на другом не виден. Остановить — `Ctrl + C` в терминале, где оно запущено.

Приложение доступно только с этого компьютера: с телефона или другого компьютера в той же сети оно не откроется. Так сделано специально: на компьютере письма со ссылкой для входа не уходят в интернет (они оседают в Mailpit), и иначе в приложение мог бы войти любой в той же Wi-Fi-сети.

## Как проверить руками

Вход — по ссылке из письма. На компьютере письма приходят в Mailpit: http://127.0.0.1:8025.

1. Откройте http://localhost:3000 — вместо списка контактов страница входа: поле «Почта» и кнопка «Получить ссылку».
2. Впишите свою почту (ту, что в `OWNER_EMAIL`) и нажмите «Получить ссылку» — появится «Ссылка для входа отправлена на …».
3. Откройте http://127.0.0.1:8025 — там письмо «Вход в Личную CRM». Нажмите в письме «Войти».
4. Вы в приложении: виден список всех контактов, сверху их количество, а в шапке — ваша почта и «Выйти».
5. Нажмите «Добавить контакт», заполните имя, нажмите «Добавить контакт» — контакт появится в списке (выделен лаймовой рамкой, с пометкой «Новый»).
6. Начните вводить имя в поиске — список сократится до подходящих людей.
7. Откройте контакт, допишите заметку в поле «Заметки», нажмите «Сохранить» (или `Ctrl + Enter` / `⌘ + Enter`).
8. Обновите страницу — заметка на месте.
9. Откройте тот же адрес в другом браузере (например, Safari, если работали в Chrome): там снова страница входа. Войдите там по новой ссылке из Mailpit — те же контакты и та же заметка. Это «второе устройство»: в первом браузере вы остались в приложении.
10. В карточке контакта внизу нажмите «Удалить контакт» и подтвердите — появится «Контакт удалён», и вы вернётесь к списку (или к результатам поиска). Контакта больше нет в списке, количество сверху уменьшилось на один. Удаление насовсем, вернуть контакт нельзя.
11. Нажмите «Группы» в шапке — откроется страница со списком групп и числом людей в каждой. Впишите название в поле «Новая группа» и нажмите «Создать» — группа появится в списке.
12. В карточке любого контакта, в поле «Группы», отметьте одну-две группы и нажмите «Сохранить» — метки выделятся, а в общем списке на главной под именем контакта появятся эти метки.
13. На главной нажмите на название группы под поиском — список сократится до людей из этой группы.

Второй пользователь и чужие данные:

1. В другом браузере нажмите «Выйти» (если вошли), на странице входа впишите любую другую почту, например `friend@example.com` — она не обязана существовать, письмо всё равно придёт в Mailpit. Войдите по ссылке из письма.
2. У нового пользователя список пуст: «Пока нет ни одного контакта» и кнопка «Добавить первый контакт». Ваших контактов и групп он не видит.
3. Скопируйте из адресной строки адрес карточки вашего контакта (`/contacts/…`) и откройте его под `friend@example.com` — «Контакт не найден».

Выход и устаревшая ссылка:

1. Нажмите «Выйти» в шапке — откроется страница входа; вход в другом браузере при этом остался.
2. Запросите ссылку два раза подряд и откройте в Mailpit первое письмо — «Ссылка устарела, запроси новую» и кнопка «На страницу входа»; по второй ссылке вход проходит.
3. Запросите ссылку четыре раза подряд на одну почту — на четвёртый раз «Слишком часто, попробуй через несколько минут»; больше трёх писем за 10 минут на одну почту не уходит.

## Автоматическая проверка

```sh
pnpm test
```

Проверяет отдельные функции приложения (например, поиск и сортировку контактов) на настоящей базе данных.
Нужны запущенные база и Mailpit (`docker compose up -d`). Команда работает в своей базе рядом с основной — с суффиксом `_test`,
пересоздаёт её перед прогоном и очищает между тестами. Ваши контакты не трогает.

```sh
pnpm test:e2e
```

Проходит главный сценарий из `specs/01-продуктовая-идея.md` в Google Chrome без окна браузера: вход по ссылке из письма, список, добавление, поиск, заметка, «другой браузер» (вход там заново, как на втором устройстве). Отдельно проверяет вход: ссылка из письма, срок и одноразовость ссылки, лимит писем, выход, чужие контакты.
Ваши контакты не трогает: создаёт рядом отдельную временную базу (с суффиксом `_e2e`) и удаляет её в конце.
Нужны запущенные база и Mailpit (`docker compose up -d`) и установленный Google Chrome; занимает около двух минут. Письма тестов остаются в Mailpit — их можно удалить на странице http://127.0.0.1:8025.

На GitHub то же самое запускается само на каждый PR в main (`.github/workflows/ci.yml`): проверка кода, оформления и типов, тесты, e2e и сборка образа. Влить PR в main можно только при зелёной проверке.

## Другие команды

- `pnpm lint` — проверка кода
- `pnpm format` — привести оформление кода к единому виду; `pnpm format:check` — только проверить
- `pnpm typecheck` — проверка типов
- `pnpm db:generate` — создать миграцию после изменения схемы в `src/db/schema.ts`, затем `pnpm db:migrate`

## Выкатка на сервер

Новая версия выкатывается сама: после merge PR в ветку `main` GitHub собирает приложение и ставит его на сервер.
Ход выкатки виден на GitHub во вкладке Actions репозитория: зелёная галочка — новая версия работает, красный крестик — что-то не так.
Выкатить ещё раз без изменений в коде: Actions → Deploy → кнопка Run workflow.

Что происходит (`.github/workflows/deploy.yml`; всё, что делается на сервере, — скрипты из папки `deploy/`):

1. GitHub собирает приложение в Docker-образ (`Dockerfile`).
2. Копирует на сервер всю папку `deploy/`: изменённые и новые скрипты попадают на сервер сами.
3. Отправляет на сервер образ.
4. На сервере (`deploy/crm-deploy.sh`):
   0. проверяет, что в серверном `.env` есть все нужные строки (список — ниже, «Настройки на сервере»); если какой-то нет, выкатка останавливается здесь, до бэкапа и миграций, и ничего не меняется;
   1. делает бэкап базы;
   2. применяет миграции базы;
   3. запускает новую версию;
   4. проверяет адрес `/health`: приложение должно ответить и назвать номер новой версии.

Ключ деплоя (секрет в GitHub) умеет только это: принять папку `deploy/`, принять образ и выкатить его.
Восстановить базу или вернуть прежнюю версию с ним нельзя — это делает только человек на сервере.
Но раз ключ привозит скрипты, через него можно поменять всё, что выкатка запускает на сервере. Поэтому изменения в `deploy/` попадают в `main` только через PR, как и остальной код.

### Если выкатка красная

Сама выкатка ничего не откатывает.

- Не получился бэкап или миграции — новая версия не запускалась, работает прежняя.
- Новая версия не прошла проверку `/health` — на сервере остаётся новая версия.
  В логе выкатки (Actions → Deploy → последний шаг) в конце написано, какой командой вернуть последнюю рабочую версию.
  Как это сделать — ниже, в «Как вернуть прежнюю версию».

### Бэкапы

Каждая выкатка первым делом сохраняет копию базы на сервере в папку `/opt/personal-crm/backups`.
Хранятся 10 последних бэкапов, более старые удаляются сами.

Пример имени: `prod_2026-11-04_09-30-15_3b5df6a….dump`

- `2026-11-04_09-30-15` — когда сделан бэкап, по UTC (московское время — на 3 часа больше).
- `3b5df6a…` — версия приложения, которая работала до выкатки: номер коммита в git, 40 символов (GitHub показывает первые 7).
  Устройство базы в бэкапе совпадает именно с этой версией.
- Окончание `_before-restore` — копия, которую восстановление сохраняет перед тем, как заменить базу.

Бэкапы лежат только на этом сервере: если пропадёт весь сервер, пропадут и они.

### Как зайти на сервер

В терминале на этом компьютере:

```sh
ssh crm
```

Дальнейшие команды из разделов ниже выполняются в этом окне, на сервере. Выйти с сервера — `exit`.

### Как восстановить базу из бэкапа

Восстановление заменяет всю базу на сервере содержимым бэкапа.
Всё, что внесли после бэкапа, из базы пропадёт — оно останется только в копии `_before-restore`.

1. Зайдите на сервер: `ssh crm`.
2. Посмотрите список бэкапов, новые сверху:

   ```sh
   sudo -u deploy /opt/personal-crm/deploy/restore.sh
   ```

3. Запустите восстановление нужного файла, подставив имя из списка:

   ```sh
   sudo -u deploy /opt/personal-crm/deploy/restore.sh prod_2026-11-04_09-30-15_<версия>.dump
   ```

4. Скрипт покажет сводку на английском и попросит подтверждение:
   - `Backup file`, `Size, saved at`, `Backup version` — какой бэкап будет загружен;
   - `Database` — какая база будет заменена; `App version now` — какая версия приложения работает (она не изменится);
   - `WARNING` — бэкап сделан при другой версии приложения, чем работает сейчас, и устройство базы может не совпасть.
     Безопаснее отменить, сначала вернуть версию из имени бэкапа (раздел ниже), потом повторить восстановление.

   Чтобы продолжить, введите `yes` и нажмите Enter. Любой другой ответ отменяет восстановление — ничего не изменится.

5. Скрипт сохранит копию текущей базы, остановит приложение примерно на минуту, удалит базу, создаст её заново,
   загрузит бэкап и запустит приложение той же версии. В конце появится строка `Restored from …`.
6. Проверьте: откройте https://app.myfirstcrm.site — данные такие, какими были в момент бэкапа.

Если в конце написано `RESTORE FAILED`: приложение остаётся выключенным, а ниже есть готовая команда,
которая вернёт копию базы, сохранённую перед восстановлением.

Пока идёт выкатка, восстановление не запустится — скрипт попросит попробовать позже.
Выкатка, которая началась во время восстановления, ждёт его окончания до 10 минут.

### Как вернуть прежнюю версию

После удачной выкатки на сервере хранятся две версии приложения: текущая и последняя рабочая до неё.
Рабочая — та, что прошла проверку `/health` при выкатке или при возврате по этому разделу.
Версия, выкатка которой упала, рабочей не считается: после неудачной выкатки на сервере есть и она, и последняя рабочая,
а следующая удачная выкатка удалит неудачную. Повторная выкатка того же коммита последнюю рабочую тоже не удаляет.

1. Зайдите на сервер: `ssh crm`.
2. Посмотрите версии:

   ```sh
   sudo -u deploy /opt/personal-crm/deploy/rollback.sh
   ```

3. Включите нужную версию (хватит первых 7 символов):

   ```sh
   sudo -u deploy /opt/personal-crm/deploy/rollback.sh 3b5df6a
   ```

   Скрипт покажет, какая версия работает сейчас и какая включится, и попросит ввести `yes`.

4. Проверьте: https://app.myfirstcrm.site/health показывает в `version` выбранную версию.

База при этом не меняется. Если новая версия уже изменила устройство базы и прежняя с ним не работает,
восстановите бэкап, в имени которого стоит возвращённая версия (раздел выше).
Следующий merge в `main` выкатит новую версию как обычно.

### Что где на сервере

Папка `/opt/personal-crm`:

- `.env` — пароль базы и настройки входа и почты (образец — `deploy/.env.example`); читать его может только пользователь `deploy`, права `600`.
- `deploy/` — копия папки `deploy/` из репозитория. Каждая выкатка заменяет её целиком, поэтому руками там ничего не правят.
- `backups/` — бэкапы базы.
- `working-versions` — список версий, которые прошли проверку `/health`, новые внизу. По нему выкатка решает, какую прежнюю версию оставить на сервере. Руками его не правят.

Приложение и база работают в Docker, проект `prod`. База на сервере своя, с базой на этом компьютере не связана.

Приложение на сервере: https://app.myfirstcrm.site. Без входа открывается только страница входа (и `/health` для проверки выкатки): вход — по ссылке из письма, которое приходит на настоящую почту.

### Настройки на сервере: вход и почта

В `/opt/personal-crm/.env` на сервере должны быть строки (значения вписывает владелец, агент их не читает и не пишет):

- `BETTER_AUTH_SECRET` — ключ, которым подписывается вход. Получить на сервере: `openssl rand -base64 32`. Секрет. Если его поменять, все выйдут из приложения и войдут заново.
- `BETTER_AUTH_URL` — адрес приложения: `https://app.myfirstcrm.site`. Из него строятся ссылки в письмах и cookie входа.
- `SMTP_URL` — через что отправляются письма: `smtps://resend:<ключ>@smtp.resend.com:465`, где `<ключ>` — ключ Resend только на отправку. Секрет.
- `MAIL_FROM` — адрес отправителя на подтверждённом домене: `noreply@mail.crm.myfirstcrm.site`. Имя отправителя «Личная CRM» зашито в приложении.
- `OWNER_EMAIL` — ваша почта. При первой выкатке входа все контакты, заметки и группы, которые уже были в базе, отдаются пользователю с этой почтой: войдёте под ней — увидите всё прежнее. Если контакты в базе есть, а строки нет, выкатка остановится на миграции с ошибкой `OWNER_EMAIL is not set…` — база не изменится и продолжит работать прежняя версия. Опечатка в этой почте — данные уйдут пользователю, под которым никто не войдёт (как исправить — в «Откат выкатки входа» ниже).

Права файла остаются `600`.

### Письма: Resend

Письма со ссылкой отправляет сервис [Resend](https://resend.com) через SMTP. Что нужно один раз:

1. Завести аккаунт в Resend и добавить домен `mail.crm.myfirstcrm.site` (отдельный поддомен для почты: основной адрес сайта не затрагивается).
2. Resend покажет записи DNS (обычно три-четыре: SPF, DKIM, подтверждение). Впишите их у регистратора (reg.ru) в зону `myfirstcrm.site` как есть. Дождитесь, пока Resend покажет домен подтверждённым (от нескольких минут до часа).
3. Создать в Resend ключ API с правом только на отправку; он и есть пароль в `SMTP_URL` выше.

Если порт 465 на хостинге закрыт — у Resend есть 2465 и 2587: меняется только `SMTP_URL`.
Если письма приходят в «Спам» или не приходят — смотрите журнал отправки в Resend.

### Откат выкатки входа

Откат только приложения (`rollback.sh`) здесь **не годится**: прежняя версия не знает про пользователей, не может создавать контакты (в базе у них теперь обязателен владелец) и показала бы всем без входа данные всех пользователей. Откатывать нужно вместе с базой и в таком порядке:

1. Зайдите на сервер: `ssh crm`.
2. Восстановите бэкап, снятый этой выкаткой. Это бэкап, в имени которого стоит версия **до** входа (самый новый из `prod_…_<версия до входа>.dump`; список — `sudo -u deploy /opt/personal-crm/deploy/restore.sh`):

   ```sh
   sudo -u deploy /opt/personal-crm/deploy/restore.sh prod_<…>_<версия до входа>.dump
   ```

   Скрипт предупредит, что версия бэкапа и работающая версия разные, — для этого отката так и должно быть, введите `yes`.
3. Сразу после этого включите прежнюю версию:

   ```sh
   sudo -u deploy /opt/personal-crm/deploy/rollback.sh <версия до входа>
   ```

   Введите `yes`. Прежняя версия ни минуты не работает с данными друзей.

Всё, что внесли в приложение после выкатки входа (в том числе контакты друзей), из базы пропадёт и останется только в копии `_before-restore`, которую `restore.sh` сохраняет перед восстановлением.

После отката исправьте причину (например, строку в `.env`) и выкатите снова обычным путём: merge в `main`.
