# Design

## Context

Мотивация — в `proposal.md`, требования — в `specs/keep-in-touch/spec.md`. Макеты экранов — по ссылке в разделе «Макеты» `proposal.md`: вид, отступы и состояния брать оттуда, правила — из требований.

Что есть сейчас:

- Таблица `contacts` (`src/db/schema.ts`): заметки — одно текстовое поле `notes`, дат у отдельных записей нет. Есть `updated_at`, но оно меняется при правке любого поля, поэтому для отсчёта не годится.
- Карточка и форма нового контакта — один клиентский компонент `ContactForm`. Значения формы — `Record<ContactField, string>` по списку `CONTACT_FIELDS` из `src/lib/contact-input.ts`. От этого списка зависят признак «есть несохранённые изменения» и показ ошибок. Проверка — общая zod-схема `contactInputSchema` для клиента и сервера.
- Шапка карточки (аватар, имя, «Кто это») рисуется серверной страницей `src/app/contacts/[id]/page.tsx` вне `ContactForm`.
- Сохранение — серверные действия `createContact` / `updateContact` (`src/app/contacts/actions.ts`), после них `revalidatePath("/")`. Поле `updated_at` Drizzle обновляет сам при каждом `update()` (`$onUpdate`), и оно показывается в карточке как «Сохранено · …».
- Главная (`src/app/page.tsx`) — серверный компонент. Рендерится на каждый запрос, потому что читает `searchParams`. Выборки — в `src/lib/contacts.ts`.
- Сообщения — `sonner`, `Toaster` подключён в общем `layout.tsx` (сверху по центру), поэтому сообщение переживает переход между страницами.
- Форматирование дат — `src/lib/format.ts`, выполняется на сервере.
- Тесты — только e2e Playwright на отдельной базе `*_e2e`, заполненной тем же генератором, что и `pnpm db:seed` (1000 контактов). Тест `main-scenario` проверяет, что строк `contact-row` на главной ровно 1000.
- В `src/components/ui` нет компонента выбора. Пакет `radix-ui`, который уже стоит в проекте, содержит примитив Select.

## Goals / Non-Goals

**Goals:**

- Считать «пора связаться» в одном SQL-запросе по данным самой базы, без фоновых задач и без хранения производных значений.
- Определять «заметку» на сервере, сравнивая с тем, что лежит в базе, а не с тем, что прислал браузер.
- Сделать «Связались» и его отмену безопасными при повторных нажатиях и второй вкладке.
- Сделать так, чтобы откат образа на предыдущую версию работал без отката миграции.

**Non-Goals:**

- Уведомления, «отложить», список «скоро пора».
- Показ срока, даты последнего общения или статуса «пора связаться» в самой карточке.
- Разбиение заметок на отдельные записи с датами и история нажатий «Связались».
- Фильтры и сортировки общего списка контактов.

## Decisions

### 1. Модель данных: четыре nullable-поля в `contacts`

- `contact_frequency` — enum Postgres `contact_frequency` (`week`, `month`, `quarter`, `year`); `NULL` значит «Не задано».
- `last_note_at timestamptz` — момент последней заметки; `NULL`, если неизвестен.
- `last_contacted_at timestamptz` — момент последнего нажатия «Связались»; `NULL`, если не нажимали.
- `frequency_set_at timestamptz` — момент, когда частота сменилась с «Не задано» на значение; `NULL`, пока частота не задана.

Почему «Связались» — отдельное поле, а не строка в заметках: так решил владелец продукта. Кнопка не правит текст пользователя и не конфликтует с несохранёнными правками заметок в открытой карточке.

Почему не одно поле «отсчёт от»: в строке блока нужно отличать «Последнее общение … назад» от «Не общались уже …» (см. спецификацию), а отмена «Связались» должна вернуть именно прежний момент нажатия.

Почему enum, а не число дней: месяц, квартал и год считаются календарными месяцами, в днях их не выразить. Рассматривали `text` + `CHECK`: enum даёт то же ограничение, а Drizzle выводит из него тип TypeScript.

Существующие строки не заполняются: моменты общения у них неизвестны, а частота не задана. Это совпадает с решением «отсчёт с момента выбора частоты».

### 2. «Заметка» и «выбор частоты» определяются одним UPDATE в базе

В `updateContact` новые моменты считаются прямо в `SET`, по старым значениям строки:

- `last_note_at = CASE WHEN notes IS DISTINCT FROM <new notes> THEN now() ELSE last_note_at END`
- `frequency_set_at = CASE WHEN <new frequency> IS NULL THEN NULL WHEN contact_frequency IS NULL THEN now() ELSE frequency_set_at END`

В `createContact`: `last_note_at = now()`, если заметки непустые, `frequency_set_at = now()`, если частота задана.

Почему так: сравнение идёт с тем, что лежит в базе, в одной атомарной операции, без лишнего чтения и без гонок. Все моменты берутся с одних часов — `now()` базы, — что и при записи, и при выборке просроченных. Альтернатива — сравнивать на клиенте с исходным значением формы — отвергнута: клиент мог отстать от базы, например если карточку меняли во второй вкладке.

Заметки уже нормализуются схемой (обрезка пробелов, пустая строка → `NULL`). Поэтому пробелы по краям изменением не считаются, а очистка заметок считается.

### 3. «Связались» и отмена — два серверных действия

- `markContacted(id)` — в одной транзакции читает прежнее `last_contacted_at` с блокировкой строки (`FOR UPDATE`) и записывает `now()`. Возвращает имя контакта, новый момент `markedAt` и прежний `previous`.
- `undoMarkContacted(id, markedAt, previous)` — `UPDATE … SET last_contacted_at = previous WHERE id = … AND last_contacted_at = markedAt`. Если строка не нашлась, значит после этого нажатия было новое или контакт удалён. Тогда ничего не меняется — ровно как требует спецификация. `previous` проверяется: это `null` или момент не позже `markedAt`.
- Оба действия не трогают `notes`, `last_note_at` и `updated_at`. `updated_at` явно оставляется прежним, иначе `$onUpdate` поменял бы «Сохранено · …» в карточке, хотя полей никто не правил.
- После обоих действий `revalidatePath("/")`. Карточку не перерисовываем: в ней ничего не зависит от `last_contacted_at`.

Почему отмена по условию `= markedAt`, а не «вернуть прежнее»: иначе отмена старого нажатия затёрла бы более новое, сделанное, например, во второй вкладке.

Сервер не запрещает «Связались» без частоты: кнопку в этом случае не показывает интерфейс, а лишняя отметка ничему не вредит.

### 4. Просроченные контакты — вычисление при чтении

Новая выборка `listDueContacts()` в `src/lib/contacts.ts`:

- начало отсчёта: `greatest(last_note_at, last_contacted_at, frequency_set_at)` (`greatest` в Postgres пропускает `NULL`);
- последнее общение для подписи: `greatest(last_note_at, last_contacted_at)`;
- конец срока: `start + interval`, где интервал по частоте — `7 days`, `1 month`, `3 months`, `1 year`. Сложение `timestamptz + interval` с месяцами в Postgres календарное и само прижимает 31 января к последнему дню февраля — ровно то, что требует спецификация;
- условие: `contact_frequency IS NOT NULL AND <конец срока> < now()`;
- порядок: конец срока по возрастанию (самый просроченный сверху), затем имя (`collate "ru-RU-x-icu"`, как в общем списке), затем `id`.

Выражения начала отсчёта, последнего общения и конца срока лежат в отдельном модуле без `server-only` (`src/db/keep-in-touch-sql.ts`). Их используют и выборка, и e2e-тест календарной арифметики.

Почему не хранить `due_at`: это производное значение, его пришлось бы обновлять при каждой правке. Генерируемая колонка тоже не подходит: `timestamptz + interval` в Postgres не immutable. Индекс не нужен: личная CRM, около тысячи строк, полный проход занимает доли миллисекунды.

### 5. Главная: серверный блок над списком

`page.tsx` вызывает `listDueContacts()` параллельно с текущими выборками и только когда поиск пуст: при поиске запроса к базе нет. Новый серверный компонент `DueContacts` (`src/components/due-contacts.tsx`) рисуется между шапкой и списком, если есть хотя бы одна строка. Внутри — заголовок «Пора связаться» со счётчиком (`Badge`) и строки по макету.

Строка — два соседних элемента, а не один. Ссылка на карточку охватывает аватар, имя и подпись. Рядом — клиентская кнопка `MarkContactedButton`: видимый текст «Связались», доступное имя «Связались — <имя>». Поэтому нажатие на кнопку не открывает карточку. После успешного `markContacted` кнопка вызывает `router.refresh()`, и строка исчезает. Если строка была последней, исчезает и весь блок.

У строк блока свой `data-testid="due-contact-row"`: счётчики `contact-row` в существующих тестах не меняются. Цвета, шрифты и отступы — только из токенов.

### 6. Сообщение «Отмечено» с отменой

`MarkContactedButton` после успеха показывает `toast.success("Отмечено: <имя>", { duration: 5000, action: { label: "Отменить", onClick } })`. `onClick` вызывает `undoMarkContacted` с `markedAt` и `previous` из ответа и затем `router.refresh()`. Если отмена ничего не изменила (было новое нажатие), отдельного сообщения нет. Ошибка сети или сервера — `toast.error` с тем же текстом, что у сохранения карточки.

Один компонент кнопки используется и в блоке, и в карточке, поэтому поведение одинаковое.

### 7. Тексты давности и частоты

- В `format.ts` добавляется `formatElapsed(from, now)`. Меньше 14 дней — в днях («9 дней»), меньше 60 дней — в неделях («5 недель»), меньше 12 календарных месяцев — в месяцах («4 месяца»), дальше — в годах («1 год»). Склонение — существующим `pluralize`.
- Подпись: есть последнее общение → «Последнее общение {давность} назад · {частота}», иначе → «Не общались уже {давность от frequency_set_at} · {частота}».
- Значения и надписи частот — в одном модуле `src/lib/contact-frequency.ts`: список значений, надписи для выбора («Раз в месяц») и для строки блока («раз в месяц»). Модуль общий для клиента и сервера.

### 8. Выбор частоты в форме

- Компонент `Select` из shadcn/ui добавляется командой CLI `shadcn`, которая уже есть в зависимостях. Новых npm-пакетов не появляется: примитив берётся из установленного `radix-ui`. Если CLI попытается добавить пакет, остановиться и спросить.
- Поле «Как часто общаться» — в первой карточке формы, после «Откуда знакомы», в половину ширины на широком экране. Под полем — подсказка из спецификации.
- `frequency` добавляется в `CONTACT_FIELDS`: значение формы — строка (`""` = «Не задано»). Так признак несохранённых изменений, ошибки и `toFormValues` работают без особых случаев. В схеме: `"" | week | month | quarter | year`, пустая строка превращается в `NULL`. Значение не из списка — ошибка проверки.
- Radix Select не допускает пустое значение у пункта, поэтому «Не задано» в самом компоненте — служебное значение `none`. Компонент переводит его в `""` и обратно.

### 9. Кнопка «Связались» в карточке

- Кнопка стоит в шапке карточки, в `page.tsx`, вне `<form>`. По макету: на компьютере справа от имени, на телефоне под именем. Она никогда не отправляет форму и не трогает состояние `ContactForm`, поэтому несохранённые правки остаются на месте.
- Видна, только если у контакта в базе сохранена частота (`contact.contactFrequency !== null`). Выбор частоты в форме без сохранения кнопку не показывает. После сохранения `updateContact` вызывает `revalidatePath("/contacts/<id>")`, шапка перерисовывается с кнопкой. Состояние `ContactForm` сохраняется, потому что у компонента прежний `key`.

### 10. Тестовые данные и e2e

- Генератор `fake-contacts.ts` детерминированно даёт примерно 3% контактов частоту, а `last_note_at` / `last_contacted_at` / `frequency_set_at` — со сдвигом в прошлое от момента заполнения. Так локально и в e2e блок сразу показывает около 10–15 просроченных контактов, а в общем списке по-прежнему 1000 строк. Нужен отдельный поток случайных чисел, чтобы имена и тексты остальных контактов не изменились.
- В e2e добавляется помощник, который через `postgres` пишет в базу `*_e2e` моменты для контакта по имени: «последняя заметка N дней назад», «Связались N дней назад», «частота выбрана N дней назад». Так тесты имитируют прошедшее время без ожидания.
- Тесты создают свои контакты с уникальными именами и проверяют только их место в блоке. Порядок проверяется относительно друг друга, а не от начала блока: сидовые контакты могут быть просрочены сильнее.

## Risks / Trade-offs

- [Исправление опечатки в старой заметке сбрасывает срок] → Принято осознанно: так решил владелец продукта, чтобы карточка осталась прежней.
- [Случайное нажатие «Связались» на телефоне вместо открытия карточки] → Кнопка отделена от ссылки, высотой 44 px. Около 5 секунд нажатие можно отменить.
- [Отмена устаревшего нажатия затёрла бы новое] → Отмена срабатывает, только если `last_contacted_at` всё ещё равен моменту отменяемого нажатия.
- [Пользователь ушёл со страницы до того, как нажал «Отменить»] → `Toaster` в общем layout: сообщение и кнопка «Отменить» остаются на новой странице.
- [Блок может стать длинным, если просрочено много контактов] → Для личной CRM ожидается немного. Если станет мешать — отдельная доработка («показать ещё»).
- [Месячная арифметика в базе идёт в часовом поясе сессии Postgres (UTC), а не по Москве] → Расхождение — несколько часов на границе месяца. Для «пора связаться» несущественно.
- [Подписи давности считаются по часам сервера приложения, а просрочка — по часам базы] → Оба сервера на одной машине или синхронизированы. Разница в секунды на тексты «N дней» не влияет.
- [Существующий тест сценария считает строки `contact-row`] → У строк блока отдельный `data-testid`.

## Migration Plan

1. `pnpm db:generate` создаёт `drizzle/0001_*.sql`: `CREATE TYPE contact_frequency` и четыре `ALTER TABLE contacts ADD COLUMN ...` (все nullable, без значений по умолчанию). Существующие строки не меняются.
2. Выкатка обычная: разовый контейнер применяет миграцию, затем стартует новый образ, затем smoke `/health`.
3. Откат — только вручную, его запускает владелец: на сервере перезапустить предыдущий образ. Миграцию откатывать не нужно: старый код выбирает колонки явно по своей схеме и новые поля не замечает.
