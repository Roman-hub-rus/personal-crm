# Design

## Context

Мотивация — в `proposal.md`, требования — в `specs/sign-in/spec.md`, `specs/data-ownership/spec.md` и `specs/contact-groups/spec.md`. Исходная спека владельца — `specs/02-пользователи-вход.md`.

Что есть сейчас:

- Входа нет. Все страницы (`/`, `/contacts/new`, `/contacts/[id]`, `/groups`) и серверные действия (`src/app/contacts/actions.ts`, `src/app/groups/actions.ts`) работают со всеми строками таблиц.
- Таблицы `contacts`, `groups`, `contact_groups` (`src/db/schema.ts`), миграции `drizzle/0000–0002`. Уникальность названия группы — индекс `groups_lower_name_idx` по `lower(name)` на всю базу.
- Выборки — `src/lib/contacts.ts` и `src/lib/groups.ts` (`server-only`), без параметра пользователя.
- Несуществующий контакт по ссылке — общий `src/app/not-found.tsx` «Такой страницы нет».
- Шапка `SiteHeader` — клиентский компонент: «Личная CRM» и ссылка «Группы».
- Миграции: на сервере — `src/db/migrate.ts`, собранный в образ (`db/migrate.mjs`), разовым контейнером `migrate`; локально — `pnpm db:migrate` = `drizzle-kit migrate`. Подготовка тестовых баз (`vitest.prepare-database.ts`, `e2e/prepare-database.ts`) вызывает мигратор Drizzle сама.
- Тесты: Vitest на базе `*_test` (подменён только `next/cache`), Playwright на базе `*_e2e` с 1000 демо-контактов. CI: задания `checks`, `e2e`, `image`, у первых двух — Postgres сервисом.
- Выкатка: `sync` папки `deploy/` (с проверкой `docker compose config` на серверном `.env`) → `load` → `release` (бэкап → миграции → новый образ → `/health`). Секреты — в `/opt/personal-crm/.env`, его пишет владелец.
- Репозиторий публичный. Чтение `.env*` агенту закрыто настройкой проекта (`Read(**/.env*)`), в том числе `.env.example`.
- Версии при планировании: `better-auth` 1.7.16, `nodemailer` 10.3.1 (типы встроены), образ `axllent/mailpit:v1.33.0`. Перед установкой — проверить последние стабильные.

## Goals / Non-Goals

**Goals:**

- Одна точка проверки запроса ссылки: почта, лимит и гашение старых ссылок срабатывают одинаково для формы и для прямого запроса к серверу.
- Владелец проверяется на сервере в каждой выборке и каждом изменении; спрятанная кнопка ничего не решает.
- Миграция переносит существующие данные к владельцу целиком или не меняет ничего.
- Одна сборка: куда уходят письма и какой адрес у приложения, решают настройки.
- Тесты на настоящей базе и настоящей почтовой заглушке; подменяется только то, что работает лишь внутри запроса Next.js.

**Non-Goals:**

- Лимит по IP (решение владельца), выход на всех устройствах, список устройств, имя пользователя.
- Защита от почтовых сервисов, которые сами «открывают» ссылки при проверке письма, — см. риски.
- Обновление Next.js и других библиотек, не нужных для входа.

## Decisions

### 1. Better Auth: таблицы и настройки

- Адаптер Drizzle (`provider: "pg"`, `usePlural: true`): таблицы `users`, `sessions`, `accounts`, `verifications` — во множественном числе, как `contacts` и `groups`. Схему пишем в `src/db/schema.ts` руками по базовой схеме Better Auth (поля в camelCase, колонки в snake_case); `id` — текст, его генерирует библиотека. Генератор схемы `auth` не ставим.
- `src/lib/auth.ts` (`server-only`) — единственный экземпляр: `baseURL` из `BETTER_AUTH_URL`, `secret` из `BETTER_AUTH_SECRET`, сессия `expiresIn` 30 дней и `updateAge` 1 сутки, встроенный лимит по IP выключен (`rateLimit.enabled: false`), телеметрия выключена, плагины `magicLink` и последним — `nextCookies`.
- `magicLink`: `expiresIn` 15 минут, `storeToken: "hashed"` (в базе не лежат работающие ссылки), `sendMagicLink` → письмо (решение 3).
- Обработчик — `src/app/api/auth/[...all]/route.ts` (`toNextJsHandler`).

Что проверено в исходниках `better-auth@1.7.16`: ссылка расходуется атомарно при первом открытии; просроченная и использованная дают один и тот же `?error=INVALID_TOKEN`; поиск и создание пользователя приводят почту к нижнему регистру, а сама ссылка — нет и пробелы не убирает; новая ссылка старые не гасит; хуки `before` выполняются и для HTTP-запросов, и для вызовов `auth.api.*`; в серверных компонентах продление сессии пропускается, потому что там нельзя записать cookie.

Почему Better Auth — задано спекой. Почему лимит по IP выключен — решение владельца; к тому же библиотека определяет IP по `x-forwarded-for`, а настройки nginx под это не проверялись, и все e2e идут с одного адреса.

### 2. Запрос ссылки: одна проверка в хуке библиотеки

Хук `before` для пути `/sign-in/magic-link` в `src/lib/auth.ts`:

1. Почта — через общую схему `emailSchema` (`src/lib/email.ts`, без `server-only`: ею же пользуется форма): обрезать пробелы, привести к нижнему регистру, проверить формат. Ошибка → `APIError` 400 с кодом `INVALID_EMAIL`.
2. В одной транзакции под `pg_advisory_xact_lock` по почте: если в `sign_in_emails` за последние 10 минут уже 3 строки этой почты → `APIError` 429 с кодом `TOO_MANY_EMAILS`; иначе записать строку, удалить свои строки старше 10 минут и удалить из `verifications` все ссылки входа этой почты — так новая ссылка гасит прежние.
3. Вернуть тело с нормализованной почтой и жёсткими `callbackURL: "/"` и `errorCallbackURL: "/login"`: прямой запрос не может увести человека на другой адрес.

Таблица `sign_in_emails`: `id`, `email`, `sent_at`, индекс по `(email, sent_at)`. Строка пишется до отправки: если почтовый сервис упал, попытка всё равно считается — так лимит не обходится сбоями.

Почему хук, а не проверка в серверном действии: обработчик `/api/auth/sign-in/magic-link` открыт в интернете, и запрос в обход формы прошёл бы мимо действия. Почему своя таблица, а не подсчёт ссылок в `verifications`: старые ссылки удаляются при новой, считать стало бы нечего. Рассматривали выключить HTTP-путь запроса ссылки и оставить только вызов из действия — тогда правило держится на настройке путей библиотеки, а хук держит его в одном месте для обоих путей.

Гашение опирается на формат записи ссылки в библиотеке (JSON с полем `email` в `verifications.value`, `identifier` начинается с `magic-link:`). Его ловит тест «Запросил новую ссылку», версия библиотеки ставится точной.

### 3. Письма: Nodemailer, настройки решают куда

- `src/lib/mail.ts` (`server-only`): транспорт Nodemailer из одной настройки `SMTP_URL` — локально и в тестах `smtp://127.0.0.1:1025` (Mailpit), на сервере `smtps://resend:<ключ>@smtp.resend.com:465`. Отправитель — `"Личная CRM" <MAIL_FROM>`, имя в коде, адрес в настройке.
- `src/lib/sign-in-email.ts` — чистая функция «ссылка → тема, HTML, текст»: тема «Вход в Личную CRM», кнопка «Войти», «Ссылка работает 15 минут», «Если вы не запрашивали вход - просто проигнорируйте письмо». У письма есть текстовая версия.
- Почтовые программы не понимают CSS-переменные, поэтому цвета и отступы письма — значения дизайн-токенов, записанные один раз константами в этом модуле. Это единственное исключение из «только токены».

Почему SMTP Resend через Nodemailer, а не HTTP-API Resend: спека требует одну библиотеку для заглушки и для Resend; выбор — настройка, код один.

### 4. Страница входа и выход

- `/login` — серверная страница с клиентской формой: поле «Почта», кнопка «Получить ссылку», ошибки под полем, после отправки — «Ссылка для входа отправлена на <почта>», поле остаётся. Вошедший → `redirect("/")`.
- С `?error=…` (так библиотека возвращает по плохой ссылке) — «Ссылка устарела, запроси новую» и кнопка «На страницу входа» (`/login`).
- Серверное действие `requestSignInLink(email)` вызывает `auth.api.signInMagicLink` с заголовками запроса и переводит коды в тексты: `INVALID_EMAIL` и ошибка формата от библиотеки → «Проверь адрес почты», `TOO_MANY_EMAILS` → «Слишком часто, попробуй через несколько минут», любая другая ошибка → «Не получилось отправить письмо, попробуй ещё раз». В ответе — нормализованная почта для сообщения.
- Серверное действие `signOut()` → `auth.api.signOut` (удаляет только сессию этого устройства, `nextCookies` стирает cookie) → `redirect("/login")`.
- Шапка: корневой `layout.tsx` берёт текущего пользователя и передаёт почту в `SiteHeader`. Есть пользователь — «Личная CRM», «Группы», почта (обрезается многоточием на узком экране) и «Выйти»; нет — только «Личная CRM». Стили — токены.

### 5. Проверка входа: страницы, действия, proxy

- `src/lib/session.ts` (`server-only`): `getCurrentUser()` — `auth.api.getSession` с заголовками запроса, кэш на запрос (`React.cache`); `requireUser()` — то же, без пользователя `redirect("/login")`.
- Каждая страница приложения и каждое серверное действие первым делом вызывает `requireUser()` и дальше работает только с `user.id`. Это и есть защита.
- `src/proxy.ts` (соглашение Next.js 16, среда Node.js) — удобство, не защита. Для страниц (кроме `/login`, `/api/auth`, `/health`, `/_next`, файлов) без cookie сессии сразу ведёт на `/login`. С cookie — запрашивает у обработчика Better Auth `get-session` как обычный HTTP-запрос и передаёт браузеру обновлённую cookie. Так заход продлевает 30 дней: серверные компоненты cookie записать не могут, а библиотека там продление пропускает.

Альтернатива продлению — клиентский запрос `get-session` из шапки после загрузки страницы: работает только с JavaScript и после отрисовки. Выбран proxy. Цена — лишний запрос к базе на каждую страницу; запись в базу — не чаще раза в сутки на устройство (`updateAge`).

### 6. Владелец в данных

- `contacts.owner_id` и `groups.owner_id`: `text not null`, внешний ключ на `users.id` без каскада — удаления аккаунта нет, а случайное удаление пользователя не должно уносить данные. Индексы по `owner_id`.
- Уникальность групп — индекс по `(owner_id, lower(name))` вместо `groups_lower_name_idx`.
- `contact_groups` не меняется. Что контакт и группа у одного владельца, держит серверный код: `resolveGroupIds` берёт `groupIds` и ищет новые названия только среди групп пользователя, вставка новых групп — с его `owner_id`, а связи пишутся только после того, как найден свой контакт. Альтернатива — `owner_id` в связях и составные внешние ключи: тяжелее миграция, а пишет в связи только этот код, и его проверяют тесты сценариев «Свой контакт в чужую группу» и «Вписал в карточке название группы другого пользователя».
- Все функции `src/lib/contacts.ts` и `src/lib/groups.ts` получают `userId` первым параметром и добавляют `owner_id = userId` в условие: `listContacts`, `listDueContacts`, `countContacts`, `getContact`, `listGroups`, `listGroupsWithCounts`, `getGroup`. Действия добавляют то же условие в `update`/`delete`/`select … for update`; ответы для чужой записи — те же, что для несуществующей.
- `src/app/contacts/[id]/not-found.tsx` — «Контакт не найден» с кнопкой «Ко всем контактам»; страница карточки по-прежнему вызывает `notFound()`, и для чужого, и для несуществующего контакта.
- Чужой номер группы в `?group=` отбрасывается сам: `parseGroupId` ищет его среди групп пользователя.

### 7. Миграция существующих данных

Одна миграция `drizzle/0003_users.sql`: `pnpm db:generate --name users`, затем SQL правится руками, снимок Drizzle не меняется (итоговая схема та же):

1. Создать `users`, `sessions`, `accounts`, `verifications`, `sign_in_emails`.
2. Добавить `owner_id` в `contacts` и `groups` — пока без `not null`.
3. Блок `DO`: если в `contacts` или `groups` есть строки — взять почту из `current_setting('crm.owner_email', true)`; пусто → `RAISE EXCEPTION` с текстом «OWNER_EMAIL is not set, but the database already has contacts or groups»; иначе создать пользователя (`gen_random_uuid()::text`, имя `''`, почта в нижнем регистре, `email_verified = true`) и проставить его всем строкам.
4. `SET NOT NULL`, внешние ключи, индексы; заменить уникальный индекс групп.

Мигратор Drizzle выполняет все новые миграции в одной транзакции: ошибка на любом шаге оставляет базу как была.

Передача почты: новый `src/db/run-migrations.ts` открывает одно соединение, проверяет `OWNER_EMAIL` той же `emailSchema` (если задана), выполняет `select set_config('crm.owner_email', $1, false)` и запускает мигратор на этом же соединении. Им пользуются `src/db/migrate.ts` (сервер и теперь `pnpm db:migrate` = `tsx src/db/migrate.ts`), подготовка тестовых баз и `src/db/migrations.test.ts`. `drizzle-kit migrate` больше не используется: он не умеет передать настройку. В лог — только «Migrations applied» и число строк, отданных владельцу, без почты.

Почему настройка, а не почта в файле миграции, — репозиторий публичный (решение владельца). Почему не отдельный скрипт после выкатки — между выкаткой и скриптом приложение стояло бы с данными без владельца.

Миграция меняет существующие данные — по CLAUDE.md её SQL показываем владельцу до merge.

### 8. Демо-данные

`seedContacts(databaseUrl, amount, ownerEmail)` находит или создаёт пользователя с этой почтой и ставит его `owner_id` всем демо-контактам и группам. `pnpm db:seed` и `node db/seed.mjs` на сервере берут почту из `OWNER_EMAIL`; без неё — понятная ошибка. Условие «только в пустую базу» прежнее. В e2e владелец демо-данных — `owner@example.com`.

### 9. Настройки

| Настройка | Что | На компьютере (`.env`) | В тестах | На сервере (`/opt/personal-crm/.env`) |
|---|---|---|---|---|
| `BETTER_AUTH_SECRET` | ключ подписи cookie, секрет | `openssl rand -base64 32` | постоянное тестовое значение в конфигах Vitest и Playwright | своё значение, секрет |
| `BETTER_AUTH_URL` | адрес приложения для ссылок и cookie | `http://localhost:3000` | `http://127.0.0.1:3100` (e2e) | `https://app.myfirstcrm.site` |
| `SMTP_URL` | куда слать письма | `smtp://127.0.0.1:1025` | то же | `smtps://resend:<ключ>@smtp.resend.com:465`, секрет |
| `MAIL_FROM` | адрес отправителя | любой, например `noreply@localhost` | то же | `noreply@mail.crm.myfirstcrm.site` |
| `OWNER_EMAIL` | почта владельца существующих и демо-данных | ваша почта | `owner@example.com` (e2e) | ваша почта |

- Тестовые значения записаны в `vitest.config.ts` и `playwright.config.ts` (это не секреты), поэтому `pnpm test`, `pnpm test:e2e` и CI работают без новых строк в `.env`.
- `Dockerfile`: на время `pnpm build` — заглушки `BETTER_AUTH_SECRET` и `BETTER_AUTH_URL`, как уже сделано для `DATABASE_URL`.
- `deploy/compose.yml`: приложению — `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `SMTP_URL`, `MAIL_FROM`; контейнеру `migrate` — `OWNER_EMAIL` (seed запускается в нём же). Все через `${…:?…}`: без строки в серверном `.env` уже шаг `sync` падает на `docker compose config` — до бэкапа и миграций, ничего не меняется.
- `.env.example` и `deploy/.env.example` — имена без значений с комментариями. `.env.example` закрыт агенту для чтения: дописать в конец, не читая, или попросить владельца.

### 10. Тесты

- Mailpit — настоящая почтовая заглушка в тестах: `docker-compose.yml` локально и сервис в обоих заданиях CI. Помощник читает письма через API Mailpit по адресу получателя; у каждого теста свои адреса, общий ящик не очищается (локально в нём и письма самого владельца).
- Vitest: `signInAs(email)` создаёт в тестовой базе настоящего пользователя и сессию через Better Auth, а `next/headers` в Vitest подменяется заглушкой, которая отдаёт cookie этой сессии, — так же, как сейчас подменён `next/cache`: оба работают только внутри запроса Next.js. Проверка сессии, база и почта — настоящие. `redirect` бросает исключение, как в Next.js.
- Сценарии со временем (15 минут, 10 минут, 30 дней) сдвигают моменты прямо в тестовой базе, как помощники `keep-in-touch` в e2e.
- Где что проверяется: правила почты, лимит, гашение ссылок, срок и одноразовость ссылки, письмо, «Большие буквы», все сценарии `data-ownership` про запросы к серверу и выборки, миграция и демо-данные — Vitest. Экраны и переходы (страница входа, сообщения, устаревшая ссылка и кнопка, шапка, выход, два устройства, 30 дней, «Контакт не найден», критерий успеха A и B) — Playwright в `e2e/sign-in.spec.ts`. «Письмо с сервера» — настоящей выкаткой (сервер без автотестов, CLAUDE.md).
- Playwright: проект `setup` входит под `owner@example.com` через Mailpit и сохраняет состояние браузера (в `.gitignore`); существующие e2e берут его и проходят как раньше. `e2e/sign-in.spec.ts` — без сохранённого состояния. В главном сценарии «другой браузер» входит заново, как второе устройство. На `owner@example.com` за прогон уходит не больше 2 писем — лимит не мешает.
- Помощники e2e, которые вставляют контакты и группы прямо в базу, ставят `owner_id` владельца демо-данных.

### 11. Выкатка и Resend

- До merge владелец: заводит Resend, добавляет домен `mail.crm.myfirstcrm.site`, вписывает записи DNS из Resend в reg.ru, создаёт ключ только на отправку, вписывает пять строк в серверный `.env`. Агент говорит, какие строки, и проверяет записи DNS через DNS-over-HTTPS.
- Выкатка обычная: `sync` (проверит новые настройки) → бэкап → миграции (данные к владельцу) → новый образ → `/health`. `/health` открыт без входа — smoke не меняется.
- nginx не меняется: адрес для ссылок и cookie задаёт `BETTER_AUTH_URL`.

## Risks / Trade-offs

- [Почтовый сервис сам открывает ссылки при проверке письма и тратит одноразовую ссылку → человек видит «Ссылка устарела»] → Проверить на почте владельца при приёмке. Если случится — отдельным изменением: ссылка открывает страницу с кнопкой «Войти», а вход — по нажатию (меняет шаг 3 главного сценария, решает владелец).
- [Нет лимита по IP: кто-то запрашивает ссылки на много разных адресов и выбирает дневную квоту Resend, владелец не может войти до следующего дня] → Решение владельца; лимит по почте не даёт завалить один ящик. Защиту по IP можно добавить отдельной правкой.
- [Гашение старых ссылок зависит от формата записи в библиотеке] → Точная версия `better-auth`, тест «Запросил новую ссылку» падает при смене формата.
- [Хостинг закрывает исходящий порт 465] → В Resend есть 2465 и 2587; меняется только `SMTP_URL`.
- [Опечатка в `OWNER_EMAIL` на сервере — данные уходят пользователю, под которым никто не войдёт] → При приёмке владелец входит и видит прежние контакты; если нет — откат (ниже), исправить строку, выкатить снова.
- [Откат только приложения: старая версия не умеет создавать контакты (нет `owner_id`) и показывает всем без входа данные всех пользователей] → Откат этой выкатки — только вместе, и в таком порядке: сначала `restore.sh` с бэкапом, снятым этой выкаткой, потом `rollback.sh` на прежнюю версию. Так прежняя версия ни минуты не работает с данными друзей. Порядок — в README.
- [Proxy добавляет запрос к базе на каждую страницу] → Для личной CRM незаметно; продление пишет в базу не чаще раза в сутки.
- [Локально `localhost` и `127.0.0.1` — разные адреса для cookie] → В README открывать тот адрес, что в `BETTER_AUTH_URL` (`http://localhost:3000`).
- [Действие передаёт библиотеке заголовки запроса, библиотека сверяет `Origin` с `BETTER_AUTH_URL`] → На сервере `BETTER_AUTH_URL` = публичный адрес; e2e на собранном приложении это проверяют.
- [Тексты на «ты» из спеки рядом с прежними на «вы»] → Допущение в `proposal.md`; владелец может поправить тексты без изменения логики.

## Migration Plan

1. До merge (владелец): Resend, домен и записи DNS, ключ; строки `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `SMTP_URL`, `MAIL_FROM`, `OWNER_EMAIL` в `/opt/personal-crm/.env` (права 600 остаются). Агент проверяет DNS и что `docker compose config` на сервере проходит — с разрешения владельца.
2. До merge: владелец смотрит SQL миграции `0003_users.sql`.
3. Merge → выкатка: бэкап (в имени — прежняя версия) → миграции → новый образ → `/health`.
4. Проверка: адрес приложения без входа — страница входа; вход под `OWNER_EMAIL` — прежние контакты, группы и заметки; число контактов и групп на сервере то же, что до выкатки (запрос через `docker compose exec`, с разрешения владельца); вход под другой почтой — пустой список.
5. Откат (вручную, запускает владелец): `restore.sh <бэкап этой выкатки>` → `rollback.sh <прежняя версия>`. Всё, что внесли после выкатки, пропадёт из базы и останется только в копии `_before-restore`.
