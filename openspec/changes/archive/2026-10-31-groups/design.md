# Design

## Context

Мотивация — в `proposal.md`, требования — в `specs/contact-groups/spec.md` и `specs/keep-in-touch/spec.md`. Макетов нет: вид экранов собирается из уже существующих компонентов и токенов, по образцу соседних экранов.

Что есть сейчас:

- Одна таблица `contacts` (`src/db/schema.ts`), миграции `drizzle/0000_*`, `0001_*`.
- Карточка и форма нового контакта — один клиентский компонент `ContactForm`. Значения формы — строки по списку `CONTACT_FIELDS` (`src/lib/contact-input.ts`), от него зависят признак «есть несохранённые изменения» и показ ошибок. Проверка — общая zod-схема `contactInputSchema` для клиента и сервера.
- Сохранение — серверные действия `createContact` / `updateContact` / `deleteContact` (`src/app/contacts/actions.ts`), каждое — один запрос без транзакции.
- Главная (`src/app/page.tsx`) — серверный компонент, состояние списка в адресе: `?q=` (поиск), `?added=`. Поиск (`ContactSearch`) сам собирает адрес `/?q=…`. Ссылки на карточку из списка несут `q`, карточка по нему строит ссылку назад «К результатам поиска» и адрес возврата после удаления.
- Выборки — `src/lib/contacts.ts` (`server-only`): `listContacts(search)`, `listDueContacts()`, `countContacts()`, `getContact(id)`.
- Список (`ContactList`) — клиентский компонент, сервер отдаёт ему только данные строк.
- Шапка сайта (`SiteHeader`) — одна ссылка «Личная CRM».
- Тесты — только e2e Playwright на базе `*_e2e`, её заполняет тот же генератор, что и `pnpm db:seed` (1000 контактов). Vitest в проекте нет.

## Goals / Non-Goals

**Goals:**

- Хранить группы так, чтобы переименование было в одном месте, а удаление группы или контакта не оставляло мусора.
- Не допустить двух групп с одинаковым названием без учёта регистра даже при одновременных запросах — правило держит база.
- Сохранять группы контакта в той же операции, что и остальные поля карточки: либо всё, либо ничего.
- Держать фильтр в адресе страницы, как поиск: без cookie и без хранилища браузера.
- Ввести Vitest и тесты на настоящей базе, не трогая существующие e2e.

**Non-Goals:**

- React Testing Library и тесты отрисовки компонентов: владелец решил пока их не добавлять.
- e2e-тесты для групп и CI — отдельное изменение позже, по решению владельца.
- Ручной порядок групп, цвета, вложенные группы, поиск по названию группы в строке поиска.

## Decisions

### 1. Модель данных: таблица групп и таблица связей

- `groups`: `id` (identity), `name text not null`, `created_at`. Уникальный индекс по `lower(name)`.
- `contact_groups`: `contact_id` → `contacts.id` и `group_id` → `groups.id`, оба `on delete cascade`; первичный ключ `(contact_id, group_id)`; отдельный индекс по `group_id` для фильтра.

Почему отдельная таблица связей, а не массив названий в `contacts`: переименование меняет одну строку, удаление группы или контакта само чистит связи (каскад), счётчики считаются простым `count`.

Почему уникальный индекс по `lower(name)`, а не проверка в коде: два одновременных запроса не создадут дубль. Рассматривали расширение `citext` — лишнее расширение Postgres ради одного поля. «ё» и «е» в названиях разные: в требованиях речь только о регистре.

Длина названия (1–50) проверяется zod-схемой, в базе ограничения нет: так же устроены остальные текстовые поля.

### 2. Общий модуль правил групп без `server-only`

`src/lib/contact-groups.ts` — правила, нужные и браузеру, и серверу, и тестам:

- `GROUP_NAME_MAX_LENGTH`, `groupNameSchema` (обрезка пробелов, тексты ошибок из спецификации);
- выбор групп в форме: добавить вписанное название (существующая группа без учёта регистра → её `id`, иначе — новое название), сравнить два выбора для признака «есть несохранённые изменения»;
- метки строки: первые три названия и число остальных;
- адреса: адрес главной по `{ query, groupId }`, адрес карточки с теми же параметрами, текст и адрес ссылки назад («Все контакты» / «К группе «…»» / «К результатам поиска»);
- разбор `?group=` из адреса и выбор группы из списка существующих (неизвестный `id` → «Все»).

Почему так: правила экрана становятся чистыми функциями, их можно проверить Vitest без отрисовки (см. решение 9).

### 3. Группы в форме контакта

- В значения формы добавляется выбор групп: `groupIds: number[]` (существующие) и `newGroups: string[]` (вписанные, ещё не созданные). Строковые поля и `CONTACT_FIELDS` не меняются. Признак несохранённых изменений = строковые поля или выбор групп отличаются от сохранённых.
- `contactInputSchema` получает `groupIds` (целые положительные, без повторов) и `newGroups` (каждое — `groupNameSchema`, без повторов без учёта регистра). Ошибки ложатся на поле `groups`.
- Форма получает от страницы список всех групп `{ id, name }[]` и держит его в состоянии: после сохранения новая группа приходит уже с `id`.
- Поле — набор кнопок-переключателей с `aria-pressed` внутри `role="group"` с подписью «Группы», по ширине карточки после «Как часто общаться». Кнопка «Новая группа» открывает поле ввода: Enter или «Добавить» — добавить метку, Escape — закрыть. Enter в этом поле не отправляет форму; Ctrl/⌘ + Enter по-прежнему сохраняет карточку.
- Если у группы, отмеченной в открытой карточке, сменили название в другой вкладке, сохранение карточки всё равно работает: связь идёт по `id`, а не по названию. Если группу удалили, её `id` при сохранении молча отбрасывается.

### 4. Сохранение карточки — одна транзакция

`createContact` и `updateContact` выполняют в одной транзакции:

1. вставку или обновление контакта, как сейчас (включая расчёт моментов «Пора связаться»);
2. `insert into groups … on conflict (lower(name)) do nothing` для `newGroups`, затем выборку их `id` по `lower(name)` — так вписанное «теннис» попадает в существующий «Теннис»;
3. итоговый набор = существующие из `groupIds` + новые; удаление лишних связей и вставку недостающих.

Ответ `updateContact` дополняется выбором групп контакта и свежим списком всех групп, чтобы форма обновила метки без перезагрузки. После сохранения — `revalidatePath("/")` и `revalidatePath("/groups")`, как сейчас для главной.

Почему транзакция: иначе при ошибке на шаге 2 поля сохранились бы, а группы — нет, хотя пользователь видит «Не удалось сохранить».

### 5. Страница «Группы» и её действия

- `src/app/groups/page.tsx` — серверная страница: `listGroupsWithCounts()` (группы по алфавиту `collate "ru-RU-x-icu"`, как имена контактов, с числом людей).
- Клиентский компонент управления: форма «Новая группа», строки с «Переименовать» (название превращается в поле на месте) и «Удалить» (`AlertDialog`, как у удаления контакта).
- `src/app/groups/actions.ts`: `createGroup(name)`, `renameGroup(id, name)`, `deleteGroup(id)`. Проверка — `groupNameSchema`. Нарушение уникального индекса (код Postgres `23505`) превращается в «Группа «<название существующей>» уже есть» — с написанием уже существующей группы. Смена только регистра у той же группы — не конфликт. Не найдена — «Группа не найдена — возможно, её удалили».
- После действий — `revalidatePath("/", "layout")`: группы видны на главной, в карточках и на этой странице.
- Счётчик «N контактов» — существующей функцией склонения из `src/lib/format.ts`.
- В `SiteHeader` справа ссылка «Группы», на странице групп — с `aria-current="page"`.

### 6. Главная: фильтр, поиск и блок «Пора связаться»

- `page.tsx` разбирает `?group=`, загружает список групп и находит выбранную. Неизвестный `id` → «Все».
- `listContacts(search, groupId)` и `listDueContacts(groupId)` получают условие `exists (select 1 from contact_groups …)`. Поиск по-прежнему не запрашивает блок «Пора связаться».
- `listContacts` дополнительно отдаёт `groups: string[]` — названия групп контакта по алфавиту, одним коррелированным подзапросом `array(…)`. Для тысячи контактов это доли миллисекунды.
- Ряд кнопок — серверный компонент из ссылок (`Link`), без клиентского JavaScript: «Все» и группы, выбранная — с `aria-current`. На телефоне ряд прокручивается вбок одной строкой, чтобы липкая шапка не разрасталась. Ряд не рисуется, если групп нет.
- `ContactSearch` получает `groupId` и собирает адрес общей функцией: смена запроса не теряет группу, смена группы не теряет запрос.
- «Найдено: N из <всего>» показывается при запросе или выбранной группе. Пустая группа и «ничего не нашли в группе» — свои тексты из спецификации.
- Ссылки на карточку из списка и из блока «Пора связаться» несут `q` и `group`. Карточка по `group` загружает название и строит ссылку назад и адрес возврата после удаления общей функцией.

### 7. Метки в строке списка

`ContactRow` под строкой «Кто это» рисует до трёх `Badge variant="secondary"` и метку «+N». Одна строка без переноса. Цвета и отступы — из токенов. У строк блока «Пора связаться» меток нет.

### 8. Тестовые данные

`seedContacts` после вставки контактов добавляет шесть групп (Семья, Друзья, Знакомые, Коллеги, Теннис, Аналитики) и раскладывает по ним примерно половину контактов, часть — в две-три группы. Для этого — отдельный поток случайных чисел, чтобы имена, заметки и данные «Пора связаться» остальных контактов не изменились. Как и сейчас, всё это только для пустой базы. Сервер не затрагивается: там групп после выкатки нет.

### 9. Vitest на настоящей базе

- Пакеты разработки: `vitest` и `vite` (обязательная зависимость Vitest), согласовано с владельцем. Версии — последние стабильные на момент установки; при планировании это `vitest 5.0.5` и `vite 8.3.5`. Команда `pnpm test` → `vitest run`.
- `vitest.config.ts`: файлы `src/**/*.test.ts` (Playwright-тесты в `e2e/*.spec.ts` не подхватываются), окружение `node`, файлы по очереди (`fileParallelism: false`) — база общая. Псевдоним `@` → `src`; `server-only` → пустой модуль, иначе `src/db` и `src/lib/contacts.ts` не импортируются вне Next.js.
- Тестовая база — `<имя базы>_test` рядом с основной, в том же Postgres в Docker. Помощник имени тестовой базы из `e2e/test-database.ts` обобщается суффиксом; защита та же — база, чьё имя не кончается суффиксом, не удаляется. `globalSetup` пересоздаёт базу и применяет миграции; перед каждым тестом таблицы очищаются (`truncate … restart identity cascade`).
- `next/cache` в тестах подменяется пустым `revalidatePath`: вне запроса Next.js он не работает, а на данные не влияет. База — настоящая, без моков.
- Уровни тестов: сценарии, которые меняют или читают данные, проверяются вызовом серверных действий и выборок на тестовой базе; правила экрана (признак несохранённого, метки «+N», ссылки назад, выбор группы из адреса) — через функции из решения 2. Каждый сценарий — свой тест с названием сценария.
- Сценарий «Существующие контакты после запуска» проверяется по-настоящему: временная база, миграции без последней, вставка контактов, затем последняя миграция и проверка, что контакты не изменились, а групп нет.
- Чисто экранные сценарии без своих данных и правил — «Групп ещё нет», «Ушёл без сохранения», «Групп нет» на странице «Группы», «Отменил переименование», «Отменил удаление» и «Поиск в группе» в блоке «Пора связаться» — без отрисовки в Vitest не проверить. Сейчас их проверяем руками по списку в `tasks.md`, автотесты на них появятся вместе с e2e. Альтернативу — React Testing Library и jsdom — владелец пока отложил.

## Risks / Trade-offs

- [`toLowerCase` в браузере и `lower()` в Postgres могут разойтись на редких символах] → Правило держит уникальный индекс в базе; браузерная проверка только подсказывает. Для кириллицы и латиницы результаты совпадают.
- [Две вкладки одновременно создают одну и ту же группу] → `on conflict do nothing` и выборка по `lower(name)`: оба сохранения попадут в одну группу.
- [Групп станет много, ряд на главной длинный] → Ряд прокручивается вбок; в карточке метки переносятся на новые строки. Для личной CRM ожидается до пары десятков групп.
- [Липкая шапка главной становится выше на строку] → Одна строка без переноса; на телефоне это ~44 px.
- [Шесть экранных сценариев пока без автотеста] → Явный список ручной проверки в `tasks.md`; e2e закроют их отдельным изменением.
- [Существующие e2e могут задеть новые элементы с похожими надписями] → Прогнать `pnpm test:e2e` локально в конце; если упадут — чинить причину в коде, тесты не ослаблять.
- [Названия групп в списке увеличивают объём данных главной] → Несколько коротких строк на контакт; в пределах десятков килобайт на тысячу контактов.

## Migration Plan

1. `pnpm db:generate` создаёт `drizzle/0002_*.sql`: две `CREATE TABLE`, внешние ключи, уникальный индекс по `lower(name)` и индекс по `group_id`. Существующие таблицы и строки не меняются.
2. Выкатка обычная: разовый контейнер применяет миграцию, затем стартует новый образ, затем smoke `/health`.
3. Откат — только вручную, его запускает владелец: перезапустить предыдущий образ. Миграцию откатывать не нужно: старый код новых таблиц не замечает, а удаление контакта в старом коде само чистит связи каскадом.
